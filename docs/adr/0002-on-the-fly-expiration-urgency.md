# 0002. Compute expiration/opened urgency on render instead of persisted alerts

Date: 2026-07-28

## Status

Accepted

## Context

The app needs to surface urgency for items that are expiring soon, opened items approaching their use-by deadline, and low-stock products, based on per-user `NotificationPreference` thresholds (e.g. "warn me 3 days before expiry").

One option is a persisted alert model — an `ExpirationAlert`-style table generated by a background worker or scheduled job, with its own dismiss/delivery-tracking state. Docker Compose already includes LocalStack, which could back a queue (e.g. simulated DynamoDB/SQS) for this. The project plan's Phase 5 also anticipates email/SMS notifications, which would need durable, delivery-tracked alerts eventually.

For the phases currently in scope (MVP through shopping/pricing), there is no delivery channel that needs durable alert state — urgency only needs to be shown in-app, live, whenever the user is looking at their inventory.

## Decision

We will not introduce a persisted alert/queue table or background worker yet. Expiration and opened-deadline urgency (expired / danger / warning / safe) is computed at render time — on dashboard/inventory page load — directly from each item's dates and the user's `NotificationPreference` thresholds. LocalStack stays in `docker-compose.yml` but is unused until a phase that actually needs it.

## Consequences

- Fewer moving parts for now: no worker process, no queue, no alert table to keep in sync with inventory state — urgency is always freshly derived from current data, never stale.
- Simpler to test and reason about: urgency is a pure function of item dates + preferences, not a separately-maintained record.
- No durable notification history and no "dismissed" state — a user can't dismiss an alert, since none is persisted.
- Email/SMS delivery (Phase 5) isn't supported by this approach and will require introducing a persisted alert/queue model at that point — this decision will need to be revisited then, not extended.
